Yüküm — a freight marketplace

Shippers post loads, carriers bid on them, the shipper picks an offer and the job is tracked until delivery and rated. I wrote the native SwiftUI app; the .NET 10 Web API and SQL Server database were built with a multi-agent AI setup under my direction.

01 — Why

A real problem from home

My family farms in Mersin. When we ship agricultural supplies, a carrier from Ankara may quote 8–10 for a trip that costs 5: if he can't find a load for the way back he drives home empty, so that risk is priced in. Carriers wait in markets for days looking for a return load. Yüküm puts both sides in one open marketplace — shippers get competing offers, carriers fill empty return trips.

03 — Features

Two roles, one product

Shipper

  • Post a load: origin / destination (province → district), weight, vehicle type, pickup date, budget
  • Compare offers with the carrier's rating, vehicle and promised delivery date; sort by 7 criteria; accept or reject
  • Live counters (views, favourites, offers) and a market reference price for the route
  • Track the job, chat, request mutual cancellation, rate the carrier

Carrier

  • Browse open loads with route, budget, vehicle, date and weight filters, a "near me" radius and "fits my vehicles"
  • Bid with a chosen vehicle and an estimated delivery date; favourite loads
  • Manage vehicles (plate, make, model, year); advance the job stage
  • Get every decision instantly through push notifications

Both roles: separate sign-up flows, auto-login, e-mail verification, forgot password, profile photo, public profiles, notification centre, report & block, account deletion.

04 — iOS

The SwiftUI app — where I spent most of my time

30 screens and 24 view models for two roles. Views only draw and forward taps; every decision lives in a view model, every request in a service, and every service goes through one client. Each folder starts with a guide file listing what is inside and which endpoint it calls.

Architecture

  • MVVM with @MainActor @Observable view models; views contain no networking or session code (audited)
  • Protocol-based DI: init(service: OfferServicing = OfferService()) — real by default, fakes in tests
  • Swift 6 strict concurrency, async/await, structured tasks (polling chat stops when the view disappears)
  • Folders: App · Design · Models (Auth, Listings, Offers, Networking, Security…) · ViewModels · Views

Networking & session

  • One generic client for every endpoint; services are one function per endpoint
  • Server errors (RFC 7807) decode once into APIError — Turkish message + machine code (e.g. email_not_verified opens the code screen)
  • AuthSession actor: access token in memory, refresh token in Keychain, device-bound; five concurrent 401s → one refresh
  • Silent restore on launch = remember me without storing the password

Platform features

  • APNs push: permission after login, token per device, tap → deep link to the right list, badge sync
  • CoreLocation "near me" radius — asked only when switched on, never stored
  • PhotosPicker profile photo, resized to a 512 px JPEG on device before upload
  • E-mail verification, forgot password with .oneTimeCode autofill, report & block (App Store 1.2)

Design & motion

  • Design system: Palette (light / dark / system), shared form components, loading states
  • Role-based action animations: shipper — a parcel gets taped / cut; carrier — a tyre track / unloading
  • RealityKit login: one box falls with physics recorded once and replayed identically, then snapshotted to an image to save battery
  • Accessibility identifiers drive 7 XCUITest flows (login, sign-up, forgot password, auto-login…)

Two pieces of the code

// One request method for every endpoint (Models/Networking/APIClient.swift)
func send<Response: Decodable>(_ method: HTTPMethod = .get, _ path: String,
                             query: [URLQueryItem] = [], body: (any Encodable)? = nil,
                             authorized: Bool = true, fallback: String = "Bir hata oluştu.")
                             async throws -> Response

let offers: [CarrierOffer] = try await api.send(.get, "/api/v1/offers/mine")

// Concurrent 401s share ONE refresh (Models/Networking/AuthSession.swift)
actor AuthSession {
    private var refreshTask: Task<LoginResponse, Error>?
    func refresh() async throws -> LoginResponse {
        if let task = refreshTask { return try await task.value }   // already refreshing → wait for it
        let task = Task { try await performRefresh() }
        refreshTask = task
        defer { refreshTask = nil }
        return try await task.value
    }
}

05 — Architecture

Clean layers on both sides

iOS (SwiftUI)                                   .NET 10 Web API
View ─► ViewModel ─► Service ─► APIClient ══HTTPS/JSON══► Controller ─► Handler ─► Repository / UoW ─► SQL Server
         @Observable   1 fn = 1 endpoint                    (thin)      (rules,      (EF Core 10)
                       AuthSession actor ◄── refresh token rotation     validation)
                       Keychain                                                  │
        push ◄══ APNs (HTTP/2) ◄── PushWorker (BackgroundService) ◄── outbox ◄──┘

Dependency rule: Domain knows nothing; Application knows only Domain and declares interfaces; Infrastructure implements them (EF Core, Identity, APNs, e-mail); Api wires everything together. Business rules are testable without a database.

One request, end to end — a carrier places a bid

  1. The detail screen calls ListingDetailViewModel.submit(), which validates the form locally.
  2. OfferService.create() → APIClient.send(.post, "/api/v1/listings/{id}/offers") adds the Bearer token. On a 401 the AuthSession actor refreshes once — even if five requests fail at the same moment — and retries.
  3. CreateOfferHandler: FluentValidation → is the listing open? → does the carrier own a complete vehicle? → is the delivery date within pickup + 90 days? → has either side blocked the other?
  4. The offer and a notification row are saved in one transaction (outbox). A background worker sends the APNs push; tapping it deep-links the shipper to the offers screen.
  5. Any failure returns RFC 7807 ProblemDetails with a Turkish message, decoded in one place and shown to the user.

08 — Database

SQL Server 2025 · 20 tables · 24 migrations

Identity users and roles, shipper/carrier profiles, vehicles, refresh tokens, provinces and districts (seeded from a verified JSON), listings, offers, messages, reviews, favourites, daily views, notifications, device tokens, blocks, reports and verification codes. Integrity is enforced in the database as well: filtered unique indexes (one active offer per carrier per listing), unique favourite / view / block pairs, cascade rules and RowVersion columns. Integration tests run every endpoint against a real SQL Server started by Testcontainers.

09 — Security & privacy

Built in, not bolted on

  • Secrets never in the repo: user-secrets locally, environment variables in production; the API refuses to start with a missing JWT key or a development e-mail sink in production.
  • Role and ownership checks on the server; an authorization-matrix test fails the build if an endpoint is accidentally anonymous.
  • Identical responses for "unknown user" and "wrong password" (plus a dummy hash check) — no account enumeration.
  • KVKK/GDPR: consent timestamps, separate terms of use, account deletion by anonymisation, profile photo deleted with the account.
  • App Store guideline 1.2: report & block with two-way effects, zero-tolerance terms.

10 — Quality

Tested and continuously integrated

Swift Testing covers every view-model function plus a contract test for each service endpoint; XCUITest drives the main flows. The backend runs every endpoint against a real SQL Server in Docker (Testcontainers). GitHub Actions builds and tests on every push.

11 — Built with a multi-agent team

How it was built: me on iOS, a team of AI agents on the backend

The brief asked for the backend to be built "with an agent mindset" — but not as "let the AI do it". So the work was split on purpose:

iOS — my code

  • I built the app screen by screen in Swift — networking, session, view models and views — with the agents explaining concepts along the way
  • For the later features I pair-programmed with the agents and reviewed every change before it went in
  • Every file is commented with what it does and what it connects to, so I can walk through any line

Backend & DB — a multi-agent team, directed by me

  • Claude Code CLI was the main agent; Codex, Antigravity and OpenCode worked as its sub-agents
  • Together they implemented the .NET API, EF Core migrations and SQL in small slices
  • Each slice: I approved the plan, the agent wrote code + tests, I checked it in Scalar and on the device, then it was committed
  • Research before decisions (2026 job ads, Microsoft & Apple docs) — recorded in 24 decision records

The order was fixed in a written plan: database → repository → handler → controller → API check → tests → iOS model → view model → view → device test → commit.
